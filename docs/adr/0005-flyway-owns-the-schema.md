# 0005 — Flyway owns the schema

Status: Accepted

## Context

The application uses JPA, which can generate and update the schema itself. That is convenient in
development and unsafe in production: Hibernate's `update` mode never drops or narrows anything,
silently diverges between environments, and cannot express a data migration.

## Decision

Flyway is the only thing that changes the schema. Hibernate runs with `ddl-auto: validate`, which
verifies that the entity mappings match the migrated schema at startup and fails fast if they do not.

Conventions, applied from the first migration:

- UUID primary keys, generated by the application.
- `timestamptz` for every point in time; the application works in UTC.
- Enum-like columns are `varchar` with **no** `CHECK` constraint, so adding a memory type or source
  needs no migration.
- Indexes are written to match a known access pattern, and the migration says which one.

Integration tests run migrations against the same Postgres image used in Compose, via Testcontainers.

## Consequences

- A mapping that does not match the schema fails at startup rather than at the first query.
- Every schema change is a reviewable, ordered, repeatable file, and the same files run in tests, in
  Compose, and in any future environment.
- Adding a field is two edits (entity plus migration) instead of one. That friction is the point.
- Migrations are forward-only; a mistake is corrected by a new migration, not by editing history.

## Alternatives rejected

- **`ddl-auto: update`.** Convenient, non-deterministic, and unable to express data migrations.
- **Liquibase.** Equivalent capability; Flyway's plain-SQL migrations are easier to review and align
  with the team's existing familiarity. No technical reason to prefer either here.
